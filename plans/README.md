## Findings considered and rejected

- **SECURITY-04 (AI remote-control no approval gate)**: not planned because the
  risk is prompt-injection-driven, not a direct code vulnerability. The system
  prompt already includes injection defenses. An approval gate is a product
  decision that changes the AI workflow UX, not a straightforward code fix.
  Worth revisiting if AI agent usage grows.
- **CORRECTNESS-02 (non-null assertions on potentially empty arrays)**: not
  worth a standalone plan. The guards exist and are correct for current code
  paths. The `!` assertions are fragile but not currently broken. Covered by
  enabling `noUncheckedIndexedAccess` (already enabled in tsconfig) and code
  review diligence.
- **CORRECTNESS-05 (IBKR double-Enter order submission)**: not planned because
  the two-Enter preview-then-submit flow is intentional UX for fast trading.
  Adding a confirmation dialog is a product decision, not a bug fix. The
  preview step serves as the confirmation.
- **PERF-03 (Bollinger band re-slices window)**: not worth a standalone plan.
  Default period (20) keeps this bounded. Only impacts users with very long
  series + high period, which is uncommon. Low ROI for the complexity of
  rolling variance.
- **PERF-07 (collectAnalyticsByPortfolio O(portfolios×tickers))**: not planned
  because typical users have few portfolios and tickers. The optimization
  requires restructuring the analytics module with MED risk for MED confidence
  impact. Not worth the effort relative to other findings.
- **PERF-08 (useTickerFinancialsMap 3× instrumentFromTicker)**: not planned.
  `instrumentFromTicker` is likely cheap per call. The 3× amplification is
  unnecessary but not a measurable bottleneck.
- **COVERAGE-01 (IBKR gateway zero tests)**: not planned as a standalone effort
  because the IBKR raw API mock surface is non-trivial to build and the risk of
  false-confidence tests is HIGH. The pure-function unit tests (suggested in
  the finding) are worth adding opportunistically when touching those files.
- **COVERAGE-02 (chat controller zero tests)**: not planned. The chat
  controller has complex external dependencies (WebSocket, storage) and the
  effort (L) is disproportionate to the leverage.
- **COVERAGE-04 (batch tests shallow)**: not planned. The existing tests cover
  the primary paths. Deeper tests are worth adding when the batch provider
  logic changes.
- **COVERAGE-05 (analytics no unit tests)**: not planned separately. If
  PERF-07 is ever addressed, tests should be added then.
- **COVERAGE-06 (remote controller market data untested)**: not planned. The
  remote controller is a mature surface with existing tests for the core path.
- **COVERAGE-07 (alert engine minimal tests)**: not planned. The alert engine
  is simple and the existing tests cover the primary condition. Edge case
  tests for malformed JSON are worth adding opportunistically.
- **TECH-DEBT-03 (widespread :any on event handlers)**: not planned. Replacing
  ~60 sites requires defining a shared event type that covers both OpenTUI and
  DOM events — a design effort with MED risk. Worth doing as part of a broader
  type-safety initiative, not as a standalone plan.
- **TECH-DEBT-04 (RPC codec in electrobun tree)**: not planned. The import
  works and the boundary test doesn't flag it. Moving the file is a pure
  refactor with no behavior change — low leverage.
- **TECH-DEBT-05 (boundary test skips test files)**: not planned. The current
  exemption is intentional — test files need to import renderer test utilities.
  Formalizing this is a nice-to-have, not a leverage point.
- **DEPS-03 (typebox abandoned)**: not planned. The migration to
  `@sinclair/typebox` has breaking API changes and the `@earendil-works`
  packages also depend on `typebox`. Coordinating a migration across multiple
  packages is a multi-team effort, not a standalone plan.
- **DEPS-04 (rxjs heavyweight for IBKR only)**: not planned. The IBKR gateway
  has complex async flows that may have subtle timing dependencies on RxJS.
  Replacing it with raw Promises is MED risk for LOW impact. Not worth the
  effort.
- **DX-01 (no linter/formatter)**: not planned. Adding a linter requires an
  initial formatting pass that creates a massive diff, disrupting ongoing work.
  This should be a dedicated effort with team coordination, not an advisor plan.
- **DX-04 (no pre-commit hooks)**: not planned. Pre-commit hooks are only
  useful after a linter is configured (DX-01). Not worth adding hooks just for
  typecheck since `bun run typecheck` is slow (~4 tsc invocations).
